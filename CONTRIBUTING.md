# Contributing

Issues and pull requests are welcome. The most valuable contribution to this project is a **sanitized payload capture from a PowerEdge model nobody has tested**, because models differ more than documentation suggests and every model-specific bug so far was found exactly that way.

## Branches

- `main` is the development branch. Open pull requests against it.
- `dist` is generated. It holds only the runtime files so users can `git clone -b dist` straight into their Domoticz plugins directory. **Never commit to it by hand**; the release workflow maintains it.
- `gh-pages` is generated by the docs workflow. Same rule.

## Development setup

```bash
git clone https://github.com/Rouzax/dell-idrac-domoticz-plugin.git
cd dell-idrac-domoticz-plugin
pip install -r requirements-dev.txt
pre-commit install
```

The runtime has **no third-party dependencies**, standard library only. Everything in `requirements-dev.txt` is for development and publishing. Please keep it that way: a Domoticz plugin that needs `pip install` is a plugin most users cannot install.

## Running the checks

The full suite runs in about a second and needs no hardware:

```bash
python3 -m pytest
ruff check . && ruff format --check .
pyright
python3 -m vulture . .vulture_whitelist.py --min-confidence 80 --exclude tests,_TEMP,docs
```

## Before you open a PR

- **Tests first.** Write the failing test, watch it fail for the reason you expect, then make it pass. Several bugs in this project were caught only because a test was written before the fix and failed differently than predicted.
- **Never weaken a test to make it pass.** If a check goes red, including one that looks unrelated or pre-existing, say so in the PR rather than adjusting the threshold, skipping it or narrowing its scope.
- Keep coverage from dropping. The pure modules carry the floor.
- Run `ruff format` on files you touch, and clear lint and type findings in those files.

### Things that are easy to get wrong here

- **`onStart` must do no network I/O.** Domoticz starts hardware synchronously, so a request to an unreachable server would stall Domoticz itself for a full timeout. The first contact happens on the first heartbeat.
- **Never write a value the server did not report.** A missing reading emits no device update at all. Domoticz keeps history, so one zero is permanent.
- **Selector levels in `control.ACTION_SLOTS` are fixed slots.** Never reorder or remove an entry, append only. Domoticz stores the level number inside scenes and timers and replays them for years, so a positional mapping would let a saved "graceful restart" become "force off".
- **Verify any new Domoticz device attribute against the core source** before relying on it. The test stub accepts any attribute, so a nonexistent one passes every test and raises against real Domoticz on every heartbeat.
- **Anything at the repo root that ends in `.py` ships to users.** The release workflow copies `*.py` into the plugin package. Dev-only Python belongs in `tests/` or `tools/`.

## Capturing fixtures from your hardware

`tools/capture_fixtures.py` fetches the payloads and replaces the service tag, serial numbers, UUID, MAC addresses and hostname with placeholders.

**Read `tests/test_fixtures_sanitized.py` before you commit a capture.** The sweep for real identifiers needs a local, untracked `tests/forbidden_literals.local.json` listing the actual strings from your machine. Without it, that test **skips** and proves nothing. The tests that need no secrets, for MAC-shaped values, private addresses and valid JSON, run either way.

Never commit the local literals file. It is gitignored and a test asserts it is untracked.

## Docs

The site under `docs/` is built with mkdocs-material and published to GitHub Pages by `.github/workflows/docs.yml` on every push to `main` that touches `docs/` or `mkdocs.yml`.

Preview locally:

```bash
mkdocs serve
```

If you change behaviour, update the docs in the same pull request. `docs/faq.md` is organised by symptom rather than by subsystem; please keep it that way.
